**Intended Architecture**

The first prototype should be a small UE5 third-person combat loop built around components, not a big RPG framework.

The player remains mostly the Third Person C++ Template character. We add number input and simple weapon/action calls. The enemy is a single prototype enemy actor, initially Goblin, with an equation component that owns the current equation, answer, rank, and evolution state. UI/Blueprints can read from C++ to display the equation, current input, and combat log.

The core flow should be:

1. Goblin owns equation: x + 5 = 10, answer 5
2. Player enters a number through a number input component
3. Player hits Goblin with an X weapon
4. Combat resolver asks enemy equation component whether input is correct
5. Correct answer executes enemy
6. Wrong answer increments enemy rank and swaps/hardens equation state
7. Operation weapons later transform the equation in a simple, explicit way

**First 5 C++ Classes / Components**

| # | Name | Type | Files |
|---|---|---|---|
| 1 | FEquationDefinition | Struct | EquationTypes.h |
| 2 | UEnemyEquationComponent | ActorComponent | EnemyEquationComponent.h/.cpp |
| 3 | UPlayerNumberInputComponent | ActorComponent | PlayerNumberInputComponent.h/.cpp |
| 4 | APrototypeEquationEnemy | Actor or Character | PrototypeEquationEnemy.h/.cpp |
| 5 | UMathCombatResolverComponent | ActorComponent | MathCombatResolverComponent.h/.cpp |

**1. FEquationDefinition**

What it does: stores prototype equation data: display text, correct answer, rank, and optional evolved equation data.

Why needed: keeps equation logic data-driven without building a symbolic parser.

Files: EquationTypes.h

Type: Struct

**2. UEnemyEquationComponent**

What it does: owns the enemy’s current equation, checks whether a submitted answer is correct, and evolves the equation/rank after wrong answers.

Why needed: this is the core equation system and should be reusable on any enemy.

Files: EnemyEquationComponent.h, EnemyEquationComponent.cpp

Type: ActorComponent

**3. UPlayerNumberInputComponent**

What it does: stores the player’s current numeric input and exposes Blueprint-callable functions like SetInputNumber, ClearInputNumber, and GetInputNumber.

Why needed: separates number entry from combat and character movement.

Files: PlayerNumberInputComponent.h, PlayerNumberInputComponent.cpp

Type: ActorComponent

**4. APrototypeEquationEnemy**

What it does: represents the first enemy, Goblin, and owns components like UEnemyEquationComponent. It exposes simple functions such as ExecuteEnemy and EvolveEnemy.

Why needed: the prototype needs one concrete enemy target for the success and wrong-answer tests.

Files: PrototypeEquationEnemy.h, PrototypeEquationEnemy.cpp

Type: Actor or Character; use Character if it needs movement/animation soon, otherwise Actor is enough for the first test.

**5. UMathCombatResolverComponent**

What it does: handles “weapon hit happened” logic. For an X weapon hit, it reads the player input, asks the enemy equation component if it is correct, then triggers execution or evolution.

Why needed: keeps combat connection separate from equation storage and player input.

Files: MathCombatResolverComponent.h, MathCombatResolverComponent.cpp

Type: ActorComponent

**Operation Behavior**
The component should mutate polynomial data directly:

- Addition operation +N:
  - Add N to the left constant term.
  - Add N to RightValue.

- Subtraction operation -N:
  - Subtract N from the left constant term.
  - Subtract N from RightValue.

- Multiplication operation *N:
  - Multiply every left coefficient by N.
  - Multiply RightValue by N.

- Division operation /N:
  - Only succeeds if every left coefficient and RightValue divide cleanly by N.
  - Otherwise returns false and leaves equation unchanged.
