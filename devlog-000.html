Devlog 000, Before the Repository

May 2026 · Origin notes · Mnemosyne

Before Mnemosyne was a repository, it was a frustration I kept running into.

I was using AI roleplay platforms, trying different bots, different prompts, and different ways to keep a scene alive for more than a few good messages. At first, I thought the problem was just that I needed a better prompt. Then I realized the problem was deeper.

The AI could write a dramatic scene. It could imitate emotion. It could produce a good moment. But it could not always live through that moment properly.

Characters changed too fast. Trust jumped too quickly. Fear disappeared because the scene needed to move forward. Shame got solved by one good speech. A character could go from guarded to devoted in a handful of messages, not because the relationship had earned it, but because the model wanted to satisfy the current direction of the scene.

That broke the illusion for me.

I did not want a character that only reacted well in the moment. I wanted a character that carried the weight of what had happened before.

My first solution was not an app. It was not a state engine. It was not even close to a real product.

It was a crude prompt system.

I built a narrator that tracked things. At the end of responses, it would keep a compact status block, almost like a little memory compile format for the scene. It tracked scene state, character condition, atmosphere, sensory details, emotional residue, and important memories.

It was messy, but it worked better than nothing.

That was the part that bothered me. If a rough prompt hack could make the experience better, then the missing piece was not just better prose. The missing piece was structure.

The AI needed a way to track continuity outside normal narration.

Not just a summary. Not just a longer context window. Not just a note saying “remember this character likes coffee.”

I wanted something that could track what changed inside a character over time.

Make the AI remember like a character, not like a transcript.

That meant tracking emotional variables separately. Trust is not the same as affection. Fear is not the same as shame. Attraction is not the same as commitment. A character can like someone and still distrust them. They can feel safe in one place and terrified in another. They can forget an ordinary conversation but remember one small sentence forever because it hit the right wound.

That became the early shape of the Soul idea.

Not a fully engineered Soul system yet. Not a database-backed memory engine. Just the idea that a character should have an evolving internal record, and that the narrator should use that record to keep the character human.

The second problem was memory quality.

I did not trust platform auto-summaries. They often flattened the wrong things, skipped important emotional turns, or preserved facts without preserving meaning. My workaround was manual: copy the whole chat, paste it into another model, and ask it to summarize the session.

That worked better, but it was still manual labor. It also proved something important: a memory system should not save everything equally.

Humans do not remember like databases. We forget most things. We keep fragments. We keep emotional landmarks. We remember what surprised us, hurt us, helped us, threatened us, or changed how we saw someone.

So the idea shifted again.

The system should not just summarize the chat.

It should track what mattered.

That led to the flagging idea. Important events and dialogue should be marked based on character-specific salience. A betrayal matters more to a character who values loyalty. A small act of protection matters more to someone who has not felt safe. A casual joke might vanish, but the same joke said during fear or grief might become unforgettable.

The system needed to decide what a character would remember, what they would misremember, and what they would forget.

It also needed to let characters grow slowly.

No instant trust. No instant healing. No emotional teleportation.

If a relationship changed, the system had to ask: was there enough time, enough evidence, enough pressure, enough consistency? If not, the character should resist the change, even if the scene wanted it.

That was when the project stopped being “I need a better RP prompt.”

It became a question:

What would it take to make AI character memory feel human?

From there, the shape of Mnemosyne started to form.

First, a crude narrator that tracked status.

Then, a better memory format.

Then, emotional progression gates.

Then, salience-based memory.

Then, the idea of a Soul that could mutate over time.

Only after that did it start to feel like something that should become code.

The narrator writes the scene. The Soul remembers what mattered.

At this point, there was no polished app. No clean UI. No roadmap. No alpha. No domain. No proper repository history yet.

There was only the feeling that the current platforms were not enough, and that maybe the fix was not another character card.

Maybe it was a system.

That is where Mnemosyne started.

Not with code.

With a crude narrator that tracked, and the suspicion that AI characters needed memory built around change, not chat history.
