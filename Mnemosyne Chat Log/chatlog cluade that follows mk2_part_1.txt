## Why "supports tool calling" ≠ consistent tool calling

Your instinct is right that it's *supposed* to be universal — there's a de-facto standard API shape (`tools` + `tool_choice` + `tool_calls`, the OpenAI schema). The problem is that "the model supports tools" only means *the endpoint accepts the parameters and the model was trained to emit them*. It does **not** guarantee it emits a schema-valid forced call every time. Three places it goes sideways:

1. **Endpoint/routing.** You're on `nex-agi/nex-n2-pro:free` through OpenRouter. The `:free` route gets sent to whcoever's hosting it cheapest, and those routes vary: some honor `tool_choice: required`, some silently ignore it, some don't pass `tools` through at all. The free/quantized variant can behave differently from the paid one with the same name.
2. **Model reliability.** Even when supported, a weaker/quantized model sometimes returns prose, or malformed JSON args, or an empty call — *probabilistically*. That's why the **same model succeeded turn 1 and fell back later in your own run**. Not your code — the model rolled differently.
3. **Schema strictness.** Your evaluator schema is big. The stricter/larger the schema, the more a marginal model fumbles it.

And to be clear from your trace: **neo CAN tool-call** — I can see it emitting perfectly valid structured ops (memories, relationship_event with axes, object states, scene state) via `tool_call`. It just doesn't do it 100% of the time on the free endpoint.

**"How do y'all code consistently?"** — you don't trust the model to be consistent; you make the *harness* consistent. That's exactly why this codebase has the ladder: `tool_call → json_schema → json_object → form_v1 → noop`, plus structural validation and bounded retries. Consistency is engineered *around* the model's flakiness, not assumed from it. A paid/stronger evaluator model would just fall back far less often.

## On "divide the tool call like a to-do list"

Right instinct about *reliability*, wrong about *speed* — and the distinction matters:

- **Smaller schema per call = less fumble. True.** A model emitting one small uniform object is more reliable than emitting a big heterogeneous union (your `EvaluatorOp` is a discriminated union: add_memory / relationship_event / update_object_state / update_scene_state — each with different required fields. That's exactly the kind of shape weak models trip on).
- **But splitting into N sequential calls = N round-trips = slower.** Each tool call is a full ~50s round-trip on this model. Split eval into 4 calls (memory / relationship / objects / scene) and you get 4×50s = 200s instead of 1×53s. The bottleneck is round-trips, not the model "thinking too hard." So "easier per call" does **not** mean "fewer seconds" when easier means *more* calls.

The way to actually capture the reliability win **without** paying for round-trips:
- **Keep it one call, make that call easier** — flatten the schema, drop optional/rarely-used fields, fewer enums, shallower nesting. Higher first-try success → fewer retries → fewer extra 50s calls. That's a speedup *and* a reliability win.
- (There's a middle option — emit *multiple small tool calls in one response* — one round-trip, uniform shapes. But weak free models are *worse* at multi-call orchestration, and it's more parsing surface. Not worth it on owl/neo-tier models.)

So: don't decompose into a sequence. Simplify the single call.
