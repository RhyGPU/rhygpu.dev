## 1. 프로젝트의 목적

Mnemosyne가 해결하려는 문제는 장기 AI 역할극에서 발생하는 다음 실패입니다.

- 중요한 사건과 약속을 잊음
- 감정과 관계가 다음 턴에 초기화됨
- 전체 대화를 계속 넣으면서 컨텍스트 비용이 증가함
- 캐릭터 성격이 점차 모델 기본 말투로 변함
- 인물·물건·장소·시간·플롯이 서로 모순됨

해결 방식은 LLM에게 모든 책임을 맡기지 않는 것입니다.

> **The narrator writes. The state map remembers.**
> 내레이터는 쓰고, 상태 지도는 기억한다.

장기적으로는 캐릭터 RP뿐 아니라 파티형 모험, 정치극, 전쟁 게임, 생존/기지 운영 등도 같은 상태 모델 위에 올리는 것이 목표입니다.

## 2. 핵심 철학

### LLM은 작가이지 데이터베이스가 아니다

LLM이 매번 전체 대화를 읽고 기억하도록 기대하지 않습니다. 엔진이 상태를 저장하고, 현재 턴에 필요한 정보만 간결한 브리핑으로 만들어 전달합니다.

### 창작과 규칙을 분리한다

- LLM: 문장, 대사, 분위기, 해석
- Rust 엔진: 검증, 점수, 관계 수치, 메모리 수명, 패치 적용, 저장

즉, LLM은 상태 변경을 “제안”할 수 있지만 최종 권위는 엔진에 있습니다.

### 기억은 로그가 아니라 살아 있는 구조다

기억은 단순 대화 저장이 아닙니다.

- 중요한 기억은 강화
- 낮은 가치의 기억은 감쇠 또는 보관
- 중복 기억은 거부·통합
- 핵심 기억은 고정
- 출처 턴과 증거를 보존
- 현재 문맥과 관련 있는 기억만 프롬프트에 주입

### 변화 속도는 상태마다 달라야 한다

즉각적인 기분은 빠르게 변할 수 있지만, 신뢰·트라우마·성격·핵심 정체성은 훨씬 느리게 바뀌어야 한다는 관점입니다. 이 철학은 RP 품질 측면에서 프로젝트의 가장 강한 차별점 중 하나입니다.

### 로컬 우선, 사용자 소유

Tauri 데스크톱 앱, SQLite, 로컬 파일 내보내기, BYO API 구조를 사용합니다. AGPL-3.0-or-later 라이선스입니다.

## 7. 코드 품질과 기술 부채

### 강점

- 상태 엔진을 별도 crate로 분리
- SQLite 모델이 예상보다 구조적

- 문서가 단순 홍보가 아니라 실패 원인과 설계 결정을 기록
- 브라우저 프리뷰와 Tauri 런타임 차이를 고려
- 세션 복구와 branch 무결성까지 고려

Rust 소스에는 단순 검색 기준으로 수백 개의 테스트 마커가 있습니다. 특히 `commands.rs`, evaluator form, DB, context compiler, provider 계층의 테스트 비중이 높습니다.

### 핵심 기술 부채

#### `App.tsx` 비대화

문서 자체에서 최근 9,419줄에서 8,298줄로 줄였다고 기록하고 있습니다. 여전히 다음이 한 컴포넌트에 강하게 결합되어 있습니다.

- 비즈니스 워크플로

- 벤치마크
- evaluator 제어
- modal 상태
- provider 상태

#### `commands.rs` 비대화

#### 프론트엔드 자동 테스트 부족

확인된 명시적 프론트엔드 테스트는 slash-command 스크립트 중심이며 이는 통과했습니다. React 화면과 주요 워크플로에 대한 정식 테스트 스택은 보이지 않습니다.

특히 위험한 흐름:

- 세션 생성/복제
- API 스트리밍
- evaluator background completion
- variant 선택과 branch 복구
- import preview/commit
- Settings 영속화

#### 문서와 코드의 시간차

Bible의 일부는 초기 설계를 반영하고 있어 현재 구현보다 뒤처졌습니다. 예를 들어 `.mne`가 “planned”로 표시된 부분이 있지만 README와 코드에는 이미 구현되어 있습니다.

#### 단일-Soul 모델과 범용 그래프 비전의 간격

현재 구조를 무리하게 확장하면 Soul JSON 안에 인물·물건·플롯이 계속 중첩될 수 있습니다. 범용 State Map을 진짜 제품 중심으로 만들려면 어느 시점에는 entity/edge/event/state를 보다 명시적인 영속 모델로 승격해야 합니다.

[React 상태 구조](https://react.dev/learn/choosing-the-state-structure), [Reducer와 Context 확장](https://react.dev/learn/scaling-up-with-reducer-and-context)

## Cognee에서 배울 부분

Cognee의 핵심은 단순 벡터 검색이 아니라 하나의 기억을 세 방식으로 동시에 다루는 것입니다.

- 회상할 때 벡터 검색과 그래프 탐색을 결합

특히 배울 가치가 큰 부분은 다음입니다.

1. **기억의 원자화**

   Cognee는 기억을 `DataPoint`라는 작은 지식 단위로 쪼개고 출처, 버전, 검색할 필드를 붙입니다. 우리도 현재 MemoryEntry보다 한 단계 세분화하여 `사실·경험·감정·믿음·인상·의도`를 연결된 기억 원자로 표현할 수 있습니다. [DataPoints](https://docs.cognee.ai/core-concepts/building-blocks/datapoints)

2. **그래프와 의미 검색의 결합**

   현재 우리 시스템은 구조화된 상태와 선별된 기억이 강점입니다. 여기에 그래프 탐색과 임베딩을 더하면 “정확히 기록된 기억”에서 “연상되는 기억”으로 발전합니다.

3. **기억 강화와 재조직**

   Cognee의 `improve`/`memify`는 기존 그래프를 다시 처리해 관계를 보강하고 중복된 엔티티를 통합합니다. 인간의 기억 공고화와 유사한 발상입니다. [Memify](https://docs.cognee.ai/core-concepts/main-operations/legacy-operations/memify)

4. **시간적 기억**

   사건의 전후 관계와 시간 범위를 검색하는 기능이 있습니다. 우리에게는 단순 날짜보다 `턴`, `세션`, `분기`, `되감기 전후`가 더 중요하므로 이를 서사형 시간 기억으로 발전시키면 좋습니다. [Time Awareness](https://docs.cognee.ai/guides/time-awareness)

5. **작고 명시적인 온톨로지**

   Cognee도 LLM이 관계명을 자유롭게 만들게 두면 표현이 흔들릴 수 있으므로 작고 고정된 온톨로지를 권장합니다. 우리에게는 `인물·경험·감정·믿음·관계·사건·장소·사물·욕망·긴장` 정도의 인간형 기억 문법이 적합합니다. [Ontologies](https://docs.cognee.ai/core-concepts/further-concepts/ontologies)

## 우리가 Cognee보다 이미 앞선 부분

Cognee는 범용 지식 기억 시스템이고, 우리는 **한 인격이 세계를 주관적으로 기억하는 시스템**입니다.

우리에게 이미 있는 중요한 차별점은:

- 객관적 세계 상태와 인물의 주관적 기억 분리
- 기억의 confidence와 truth status
- 관계 수치와 감정적 변화
- 사건 및 상태 패치 원장
- 되감기와 재생성
- 컨텍스트 예산에 맞춘 기억 선별
- Narrator와 Evaluator의 책임 분리

Cognee식 그래프를 그대로 따라가면 모든 것을 “지식 사실”로 평탄화할 위험이 있습니다. 인간형 기억에는 아래 셋이 반드시 분리돼야 합니다.

> 실제 발생한 것
> 인물이 경험한 것
> 인물이 그렇게 믿는 것

이 차이가 우리 시스템의 핵심 철학이고, Cognee에는 상대적으로 약한 부분입니다.

Cognee처럼 제품 전체를 바꾸기보다는 현재 구조 위에 **Associative Memory Layer**를 추가하는 방향이 가장 좋습니다.

[코드 블록 생략]

기억은 앞으로 이런 구조가 적합합니다.

- **Episodic memory:** 언제, 어디서, 누구와 무엇을 경험했는가
- **Semantic memory:** 여러 경험을 통해 무엇을 사실이라고 학습했는가
- **Emotional memory:** 무엇이 어떤 감정을 유발했는가
- **Relational memory:** 누구를 왜 신뢰하거나 경계하는가
- **Prospective memory:** 앞으로 하려고 했던 일, 약속, 미해결 의도
- **Self memory:** 나는 어떤 존재라고 생각하는가
- **Uncertain memory:** 추측, 소문, 오해, 왜곡된 기억

그리고 회상은 단순 유사도 순위가 아니라 다음을 합산해야 합니다.

`관련성 + 최근성 + 중요도 + 감정 강도 + 관계 강도 + 인과 거리 + 현재 목표 + 기억 신뢰도`

## State Map과 Neural Map

첨부한 화면 같은 **State Map은 유지하는 게 좋습니다.** 이것은 현재 상태를 빠르게 이해하는 운영 화면입니다.

Neural Map은 별도 화면 또는 별도 렌즈가 적합합니다.

- State Map: 지금 무엇이 사실인가
- Memory Map: 무엇을 기억하고 있는가
- Neural Map: 기억들이 어떤 연상 구조로 연결돼 있는가
- Relationship Map: 누구와 어떤 사건 때문에 관계가 변했는가

Cognee의 기본 그래프 시각화는 노드·관계·가중치를 탐색하는 일반적인 지식 그래프에 가깝습니다. 그대로 복제하면 큰 그래프가 금방 복잡해집니다. [Graph Visualization](https://docs.cognee.ai/guides/graph-visualization)

우리 Neural Map은 예쁜 전체 그래프보다 **선택한 인물이나 기억을 중심으로 1~2단계 연결만 보여주는 인간 중심 탐색기**여야 합니다. 추론된 연결은 점선, 거짓이거나 폐기된 기억은 흐리게, 감정적으로 강한 기억은 크고 진하게 표현하면 시스템 철학과도 잘 맞습니다.

정리하면:

> Cognee는 우리의 교체 대상이 아니라,
> **“기억을 그래프화하고 연상 회상하는 법”을 배우기 좋은 레퍼런스**입니다.

다음 발전 순서는 **기억 유형 체계화 → 기억 간 그래프 관계 → 하이브리드 회상 → Neural Map 시각화**가 맞습니다. 시각화부터 만들면 보기에는 멋지지만 내부 기억 모델이 빈약해서 결국 장식이 됩니다. 먼저 인간형 기억 온톨로지와 회상 공식을 설계하는 게 다음 작업으로 가장 좋습니다.

- 직접 경험

- 약속이나 미해결 의도

- 반복 경험을 하나의 의미 기억으로 압축
- 인물에 대한 신념 강화 또는 약화
- 모순 기억 탐지
- 스키마 형성
- 중요하지 않은 기억 감쇠
- 여러 사건의 인과 연결

이 작업은 Narrator 응답을 막지 않고 비동기로 돌릴 수 있습니다.

### 회상 시

LLM이 전체 기억을 검색할 필요도 없습니다.

1. 로컬 엔진이 정확한 인물·장소·사건을 찾음
2. 벡터 검색으로 의미가 가까운 기억을 찾음
3. 그래프에서 주변 기억을 확장
4. 상위 후보만 필요하면 소형 AI가 재순위화
5. Context Compiler가 최종 토큰 예산을 적용

따라서 기억이 수천 개가 되어도 Narrator에게는 매번 5~10개의 정제된 기억만 전달됩니다.

## 필요한 핵심 구조 변경

현재 시스템을 폐기할 필요는 없고, 책임을 다음처럼 분리하면 됩니다.

- `State Engine`: 실제 세계와 객관 사건의 정본
- `Memory Formation`: 사건을 주관적 경험으로 변환
- `Memory Consolidation`: 경험을 신념·스키마로 발전
- `Memory Index`: 시간·그래프·벡터 인덱스
- `Recall Engine`: 현재 상황에 반응하는 연상 검색
- `Context Compiler`: 최종 프롬프트 편성
- `Narrator`: 편성된 정신 상태를 바탕으로 서술

5. graph/vector DB에 저장
6. 필요할 때 다시 검색하고 reasoning

V2 cascade는 node 추출, 관계명 추출, edge triplet 추출을 여러 LLM pass로 나눈다. 즉 마술적인 단일 프롬프트가 아니라 **복수의 작은 추출 호출 + 타입 검증 + 그래프 저장**으로 성공시킨 것이다. [Cognee graph extraction](https://github.com/topoteretes/cognee/blob/main/cognee/tasks/graph/extract_graph_from_data.py), [Cognee V2 cascade](https://github.com/topoteretes/cognee/blob/main/cognee/tasks/graph/extract_graph_from_data_v2.py)

## 최종적으로 우리 구조가 가져갈 것

Hindsight나 Cognee를 그대로 복제하는 것보다 이 혼합 구조가 좋다.

[코드 블록 생략]

결론은 이거다:

- `Narrator + extraction`을 한 프롬프트에서 하지 않는다.
- 서술 후 별도의 structured extraction을 실행한다.
- Extractor는 점수가 아니라 근거 있는 행동 후보를 낸다.
- Compiler가 점수를 계산한다.
- Hindsight의 강점은 검색·reflection·mental model이다.
- Cognee의 강점은 다단계 graph extraction이다.
- 우리만의 핵심은 여기에 **재현 가능한 동적 심리 상태기계**를 합치는 것이다.

그러니까 eval/local repair가 전부 쓸모없어진 게 아니라, 역할이 바뀐 거다. **Evaluator는 Extractor로 단순화되고, Repair 모델은 로컬 Extractor 후보가 되며, 최종 권한은 Compiler에 남는다.**
