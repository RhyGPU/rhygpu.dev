# Between Dawns 정식 V1 시스템 완성 알파 구현 계획

## 요약

- Godot 4.3 기반 네이티브 프로젝트로 Android ARM64와 Windows x64를 우선 지원한다.
- 비공개 최대 6인 협동 알파를 목표로 문서의 Phase 1~4를 모두 구현한다.
- Phase 5의 차량·로봇·외교와 Future Ecology의 실제 Hive·Colony·변이는 제외하되, 향후 호환되는 데이터 필드는 미리 둔다.
- 그래픽·음향은 코드 기반 임시 에셋을 사용하고 시스템, 네트워크, 세이브, 플레이 루프의 완성도를 우선한다.
- 현재 단일 수직 슬라이스는 기능 참고용으로 유지하되, 서버 권위형 구조에 맞게 모듈화한다.

## 핵심 아키텍처와 인터페이스

- `scripts/game.gd`를 얇은 조립 계층으로 축소하고 `core`, `simulation`, `network`, `ui`, `data` 모듈로 분리한다.
- Listen Server와 Headless Dedicated Server가 동일한 `SharedSimulation`을 사용한다.
- ENet UDP 직접 접속을 사용하며 기본 게임 포트는 `24560`, LAN 검색 포트는 `24561`로 한다.
- 최대 6명, 서버 시뮬레이션 20Hz, 입력 30Hz, 스냅샷 10Hz, 클라이언트 보간 버퍼 120ms를 기본값으로 한다.
- 서버가 이동 검증, 전투, RNG, 아이템, 건축, NPC, Squad, Zone, 세이브를 소유한다. 클라이언트 예측은 플레이어 이동과 조준에만 적용한다.
- 주요 요청 타입은 `InputFrame`, `InventoryTxn`, `InteractRequest`, `BuildRequest`, `RTSOrder`, `SquadMissionRequest`, `DirectControlRequest`로 고정한다.
- 아이템 이동은 `txn_id`, 출발/도착 컨테이너, 아이템 ID, 수량, 예상 revision을 포함하는 원자적 트랜잭션으로 처리한다.
- 핵심 데이터 리소스는 `ItemDef`, `RecipeDef`, `StructureDef`, `ZoneDef`, `NPCState`, `SquadState`, `ConfirmedEvent`, `WorldConfig`로 정의한다.
- `WorldConfig.death_policy`는 월드 생성 시 고정한다.
  - 기본 `INDIVIDUAL_ELIMINATION`: 사망 플레이어는 해당 월드에서 영구 관전.
  - 선택 `FRESH_REJOIN`: 60초 관전 후 초기 능력치의 새 캐릭터로 해방된 작전소에서 합류. 기존 장비는 시체에 남긴다.
- 연결 종료 시 서버 AI가 캐릭터를 인계해 가장 가까운 해방 거점으로 복귀시킨다. 이동 중 부상과 사망 가능성은 유지한다.
- 호스트 이전, 계정, 중앙 서버 목록, 릴레이, 매치메이킹은 V1에서 구현하지 않는다.

## 구현 단계

### 1. 권위 서버·저장·데이터 기반

- 시작 화면에 새 월드, Listen Server, Dedicated Server, IP 접속, LAN 검색을 제공한다.
- 월드 세이브는 manifest, 압축 Zone 스냅샷, 플레이어/NPC 상태, append-only transaction journal로 분리한다.
- 5분마다 자동 체크포인트를 만들고 사망, 건축 완료, Zone 해방, 대형 아이템 거래 직후 추가 저장한다.
- 임시 파일 작성 후 원자 교체하고 최근 정상 백업 3개를 유지한다.
- 세이브 schema version과 마이그레이션 레지스트리를 처음부터 적용한다.
- 비공개 알파 인증은 설치 UUID와 닉네임만 사용하며 보안 계정 시스템은 제외한다.

### 2. Core Survival과 무한 Zone Graph

- 32px 타일 기준 64×64 크기의 유한 Zone을 seed로 생성하고 출구를 통해 무한 graph로 확장한다.
- 감염 도시, 유령도시, 농지, 교외, 산업단지, 고속도로의 6개 Zone 유형과 biome adjacency 규칙을 구현한다.
- 미방문 Zone은 seed와 metadata만 저장하고 첫 진입 때 생성한다. 방문 후 타일, loot, 건축, contamination, control state를 영구 보존한다.
- 플레이어가 있는 Zone은 Full Simulation, 빈 Zone은 Abstract Simulation, 같은 Zone의 관심 영역 밖 entity는 저주기 업데이트한다.
- 낮/밤, 날씨, 소음, 인원수, 정착지 규모, Zone Pressure로 Spawn/Horde budget을 계산한다.
- `INFECTED → CONTESTED → LIBERATED` 상태와 외부 출구를 통한 재유입, 영토 포기와 철수로를 구현한다.
- 알파 콘텐츠 최소치는 아이템 48종, 총기 6종, 근접무기 4종, 방어구·공구 11종, 제작법 28개로 고정한다.
- 건축물 14종을 제공한다: 벽, 문, 저장고, 침상, 농지, 작전 테이블, Clinic, Workshop, Guard Post, 발전기, UV 방어등, 화덕, 집수시설, Base Radio.
- 총기 탄약, 재장전, 명중, 내구도, jam, 반복 수리 시 최대 내구도 감소를 구현한다.
- 피해는 부위·출혈·감염 노출을 기록하며 `Healthy → Injured → Downed → Dying → Dead`로 진행한다.
- 실내 시체 소각은 방 단위 aerosol contamination을 생성하고 문·창문·환기에 따라 확산·감소시킨다.

### 3. NPC·교대·RTS

- NPC는 5개 Attribute, 8개 Skill, 7개 Personality 축, Trait, Mental, Fatigue, Injury, Equipment, Experience를 가진다.
- 음식·화장실 같은 개별 생활 욕구는 구현하지 않는다.
- Profession은 NPC 클래스가 아니라 Workstation과 Assignment로 결정한다.
- 하루를 3개 Shift로 나누고 기본 스케줄은 AVAILABLE 2개, REST 1개로 한다.
- 작전 테이블 이전에는 Follow, Move, Defend만 허용한다.
- 작전소 Level 1에서 교대·Job, Level 2에서 Squad·원거리 임무, Level 3에서 선발 NPC 직접조작을 해금한다.
- PC는 드래그 선택과 우클릭 명령, 모바일은 NPC 탭 선택·선택 추가 버튼·명령 휠을 사용한다.
- Move, Attack, Defend, Patrol, Follow, Scavenge, Haul, Build, Repair 명령을 제공한다.
- 직접조작 중인 NPC의 고유 능력치·Mental·Fatigue·장비·부상을 그대로 적용하고 동시에 두 플레이어가 같은 NPC를 조작하지 못하도록 서버 lock을 건다.
- 모바일은 왼쪽 이동 스틱, 오른쪽 조준 스틱, 별도 사격 버튼을 사용한다. 자동조준 보조는 기본 35%이며 설정에서 0~100%로 조절한다.

### 4. 원거리 Squad·무전·현장화

- 원거리 Squad는 members, Zone/POI, mission, phase, equipment summary, threat context, confirmed events, radio status, last contact를 저장한다.
- Abstract Simulation은 서버에서 결정론적으로 실행하며 탄약 소비, 부상, 사망, 획득물, 이동 상태를 즉시 확정한다.

- 무전이 없으면 마지막 위치와 예상 귀환 시각만 표시하고, 무전이 있으면 주요 사건을 실시간 텍스트로 전달한다.

35. 제일 중요한 Anti-Bullshit Rule

우리 RNG에는 이 룰을 박아야 함.

Randomness may create risk. It should rarely create irreversible loss in one step.

Event RNG
↓
Danger
↓
Player/NPC response
↓
Check
↓
Complication
↓
Possible Down
↓

↓
Death

“D100=1, Medicine 93 NPC 사망” 금지.

그러면 Permadeath가 억까가 아니라 플레이어가 감수했던 위험의 결과가 됨.

36. 최종 Backend Flow

이게 내가 처음부터 만들어줬어야 했던 그림임.

│

              │

이 설계의 핵심은 세 가지임.

첫째, 모든 Text Event가 동일한 수학 엔진을 사용한다. 총격전, 수색, 치료, 설득, 수리마다 별도 임의 RNG를 만들지 않는다.

둘째, Skill/Personality/Mental/Fatigue/Equipment가 모두 같은 판정에 실제로 물린다. 그래서 캐릭터 시트에 있는 숫자 중 “보여주기용” 숫자가 없어야 한다.

셋째, RNG는 결과를 만들어내는 주인공이 아니라 불확실성을 제공한다. 결과의 대부분은 누구를 보냈고, 어떻게 키웠고, 뭘 들려줬고, 어떤 상태에서 보냈는가가 결정하고 RNG는 그 사이를 흔든다.

이게 A Legionary's Life가 RNG 게임처럼 보이면서 실제로는 준비·능력·상황이 확률을 지배하는 방식에서 가장 크게 배워올 점이라고 봄. 개발자도 실제 성공 확률을 그대로 표시하고, 같은 75%라도 이전 실패와 독립적으로 다음 판정은 다시 75%라고 명시한다.

이제야 네가 말한 **“text RPG에서 배워온 RNG 및 backend 계산”**에 맞는 답이다.
