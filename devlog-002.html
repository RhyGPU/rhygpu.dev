Mnemosyne Devlog

Devlog 002, Making Hidden State Work

The App Started Testing the Soul

April 2026 · Early repository phase · Hidden state, app scaffolding, and real model testing

Before the repository existed, Mnemosyne was still mostly living inside chats, prompts, and messy experiments.

The crude code block existed.

The Soul idea existed.

The psychology and memory foundation was starting to exist.

But none of that was really a project yet. It was still pre-repo work, the kind of thing that lives in conversations, notes, and local experiments until you finally decide it is worth protecting.

That changed after I started looking into open-source licensing.

I did not want to build something that could just be swallowed, closed off, or copied without giving anything back. The license question was part of the moment where Mnemosyne stopped feeling like a disposable prompt trick and started feeling like something I actually intended to build.

So the repo began.

The first commits were not glamorous. They were foundation work: setting up the repository, adding the AGPL license, declaring that license in the package metadata, and merging the initial GitHub repository state.

It was not “the app” yet, but it was the moment Mnemosyne stopped being only a pile of prompts and became something with a protected project boundary.

Then came the desktop client scaffold.

That was the line.

Before that, Mnemosyne was an idea with experiments behind it.

After that, it was software.

Not finished software.

Not good software.

But software.

The first real shape was a local desktop client: Tauri, React, Rust, Soul files, local persistence, context compilation, and hidden state parsing. The project was moving out of pure prompting and into an app that could actually hold state outside the model.

That mattered because the question changed.

Before, I was asking:

Can I make the AI remember better with a prompt?

Now, I was asking:

Can an app take what the AI reports, hide the messy machinery from the user, and update the Soul behind the scenes?

That was a completely different problem.

The crude code block from the earlier experiments had become a prototype for hidden state. It was supposed to sit behind the narration, not inside it. The user should see the scene, the emotion, the character, and the atmosphere.

They should not see the machinery.

No ugly JSON.

No memory tags.

No trust deltas.

No retrieval scores.

No system residue.

No visible code box sitting under every reply, reminding them that the character is being calculated.

That part was harder than it sounded.

At first, the code block was useful because it was visible. I could inspect it. I could see whether the AI was tracking memories, emotional shifts, scene details, and character state. But if Mnemosyne was going to become an actual RP client, that block could not stay in the user-facing experience forever.

The app had to separate two things:

What the player sees.
What the engine reads.

That became one of the first real technical problems.

The narrator response needed to stay clean.

The hidden state needed to be machine-readable.

The app needed to strip the hidden state from the visible response, parse it, apply it to the Soul, and then store the updated result. If the hidden state leaked into the chat, it broke immersion. If it disappeared completely, the engine lost the update packet.

Both failures were bad.

So the turn flow started becoming real.

User message.

Compiled context.

Model response.

Visible narration.

Hidden state.

Parser.

Soul update.

Memory scoring.

Consolidation.

Save.

Repeat.

That loop was the first version of Mnemosyne actually breathing.

The first turn-flow commits were mostly about making the app behave like an app. The chat interface needed to send something, receive something, and prove that a hidden-state block could exist inside the pipeline.

That led to the early mock provider wiring and later mock acceptance coverage.

But I do not want to oversell that mock.

The mock was not where the real RP testing happened.

It was basically an early placeholder for the chat interface and turn flow. It could return a fixed kind of answer, attach a predictable hidden state block, and make the UI look like it was doing something. That was useful for shaping the app before the real provider path was ready.

But as a test of roleplay, memory, or narration, it was useless.

It did practically nothing.

The real testing came from actual LLMs.

I was already a heavy AI RP experimenter, and I had been using OpenRouter to try different models. So when I needed real generations for testing, free OpenRouter models became the obvious choice.

I needed to see whether the system actually held together when a real model answered. A fake response could prove that the button worked. A real model could prove whether the idea survived contact with chaos.

That was where the useful failures came from.

A real model might forget to include the hidden state.

A real model might reveal the code block to the user.

A real model might wrap the hidden state in the wrong format.

A real model might summarize instead of updating.

A real model might keep adding memories instead of decaying them.

A real model might understand the rule, explain the rule, and then fail to follow the rule three turns later.

That was the kind of failure I needed to see.

The mock could help the app have a shape.

The real models tested the system.

Once the pipe existed, the next problem was making the state less visible and more machine-readable. That led to encoded hidden state, API hidden-state prompt alignment, and debug tools for inspecting the turn cycle without exposing the raw machinery to the player.

Then came the second hard problem:

Forgetting.

I already knew I did not want Mnemosyne to save everything. That would just recreate the same problem in a different form. A giant memory list is not intelligence. It is hoarding.

But making a system forget in a human-like way is not simple.

If memory decays too aggressively, the character becomes shallow.

If memory never decays, the character becomes a database.

If every emotional moment becomes permanent, nothing is actually important.

If nothing becomes permanent, the character never grows.

That balance was the heart of the Soul.

The goal was not just to delete old entries.

The goal was to decide what should fade, what should merge into a pattern, and what should become part of the character.

A boring repeated event should disappear.

A repeated kindness might become trust.

A repeated threat might become fear.

A repeated silence might become abandonment.

So forgetting could not just be a timer.

It needed meaning.

At first, I was still trying to make the LLM handle that inside the hidden state.

The model had the scene. It knew the emotional context. It could judge what mattered. So it felt natural to let it propose memory entries, emotional tags, retrieval strength, and what should fade or stay fresh.

In theory, that sounded fine.

In practice, it was asking one generation to do too much.

It had to write the scene, stay in character, follow lore, avoid speaking for the user, hide the code block, update relationship values, flag memories, and also remember to decay old ones correctly.

Sometimes it followed the rule.

Sometimes it explained the rule.

Sometimes it even performed cleanup when I directly forced it with an OOC command.

But it was not reliable.

That was the uncomfortable part.

I was building an engine, but I was still asking the model to behave like part of the engine.

At first, I did not fully see the problem. I was more focused on getting the hidden state to appear, disappear from the user-facing chat, and update the Soul at all.

Then the pattern started to show.

The character was not really forgetting.

The memory list kept growing.

Old entries stayed too strong.

The system could talk about decay, but it did not consistently decay.

That was when the question changed again.

Not:

How do I prompt the AI well enough?

But:

I need a separate layer to unload the burden.

I thought hard and came to the conclusion that the AI should tell the code how important something is, and the code should take over and decay or preserve it based on rules.

The LLM writes the scene.

The hidden state reports candidate changes.

The app hides and parses the machinery, then starts taking responsibility for managing memory.

The Soul updates every turn.

The player sees only the story.

That sounds obvious now, but it took testing to make it obvious.

The hardest parts were not the dramatic ones.

They were small, annoying, practical things.

How do I stop the AI from showing the hidden state to the user?

How do I parse the hidden block safely?

How do I test the interface before the real model path is stable?

How do I make the LLM judgment reliable?

Those problems made the project feel real.

Not because they were exciting, but because they were the kind of problems apps have.

The moment Mnemosyne had to hide the code box, parse it, and update a Soul file, it stopped being only a prompt experiment.

It became software.

The AI was still important.

The prompt was still important.

The hidden state was still important.

But the lesson was becoming clear:

The LLM should write and evaluate.
The engine should manage.
The Soul should change.

The lesson was not that the engine had already solved the memory.

It had not.

The lesson was that the boundary had to move.
