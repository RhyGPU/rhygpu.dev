These are the issues

1. Memory quality is now more important than token savings.
The system already saves a large amount of context by using compact memory/state instead of full chat history. The next hard problem is making sure the small amount of memory retrieved is the correct memory.

2. Memory residue and cross-session bleed must be controlled.
If imported logs, previous sessions, or parallel-session memories are not clearly labeled, the character may treat them as direct lived experience. This can be interesting for story, but dangerous as an accidental default.

3. Memory retrieval needs category slots, not just top memories.
Recommended slots:
- relationship memories
- current-plot memories
- character-identity memories
- unresolved-tension memories
- world/location memories
- recent emotional-state memories

4. Memory hygiene needs to be stricter.
Reject or deprioritize low-value memories such as:
- “She felt tense”
- “She looked at the user”
- “She listened carefully”
- repeated body language
- generic emotional reactions

Prefer durable memories such as:
- relationship turning points
- promises
- betrayals
- identity changes
- unresolved conflicts
- important world facts
- major character self-concept changes

5. Entity separation is mandatory.
The engine must distinguish:
- developer/operator
- player character
- narrator-controlled NPC
- imported-log speaker
- current user
- previous-session user/persona

Relationship state should be per-entity. Aurora should not automatically transfer distrust, affection, fear, or comfort from Junhwa to Rhy unless the story actually justifies it.

6. Active plot state needs lifecycle management.
Recommended structure:
- dominant_current_plot
- background_plots
- resolved_plots
- stale_plot_decay

This prevents old conflicts from staying sticky forever.

7. Pasted logs need import mode.
Do not send giant pasted logs directly to the narrator. Route them through a summarizer/state-updater pipeline first, extract memories/events/entities/relationships, then give the narrator a compact result.

8. Anti-replay protection should be mechanical.
Prompting alone is not enough. The engine should compare new narrator output against recent assistant responses and reject/regenerate near-duplicates.

9. Sequential architecture should be optimized for UX.
Recommended flow:
- compile context
- stream narrator response immediately
- save visible response
- run state updater in the background
- apply patch before the next turn when possible

The user should not wait for the updater unless they send the next message before the updater finishes.

10. Add timing metrics.
Track:
- context_compile_ms
- narrator_first_token_ms
- narrator_done_ms
- state_updater_done_ms
- db_save_ms
- total_turn_ms

This will show whether slowness comes from the model, provider routing, output length, updater, or local app code.

11. Add speed presets.
Recommended modes:
- Fast: shorter responses, lower output token target
- Balanced: normal RP mode
- Literary: longer, more detailed prose

12. Updater model can be cheap/free, but needs validation.
The updater does not need to be a powerful prose model. It needs to reliably return valid JSON patches. Use cheap/free models when possible, but add fallback if JSON validation fails or rate limits occur.

13. Honest performance claim.
Do not claim guaranteed token savings. Better wording:
“In long RP/story sessions, Mnemosyne is designed to reduce context growth by sending compact state, memory, relationship, and world summaries instead of resending the full chat history every turn.”

14. Still not production-final.

- portable .mne bundle import/export
